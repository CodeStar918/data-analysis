# 企业内网自然语言报表生成平台 — 项目设计方案

> 定位：企业内网数据查询与结果生成平台。员工上传 Excel 或选择数据库表，用一句中文描述需求，系统借助本地 Ollama 大模型解析意图，自动生成**统计表**或**明细表（原字段 + 新增计算字段）**。数据不出内网。

---

## 一、项目总体目标

1. 员工上传 Excel 或选择数据库表作为数据源。
2. 员工用自然语言描述需求，例如：
   - “按区域和月份统计销售额合计，只看 2024 年，生成统计表。”
   - “给订单明细表增加一列：是否紧急，如果交货天数小于 3 且金额大于 5000 就标记为紧急，否则标记为普通。”
3. 系统借助本地 Ollama 大模型解析需求，生成 SQL 或数据处理逻辑。
4. 生成两类结果：
   - **统计表**：新增一个汇总结果表。
   - **明细表**：保留原数据明细，并在原表基础上新增计算字段，供后续人工分析。

系统部署在公司内网，数据不出内网。

**背景痛点**：
- 公司大量报表以 Excel 为主，报表人员素质参差不齐，很多人不会基础 Excel 操作。
- 公司已有服务器、内网、SQL 数据库、Ollama 等软硬件设施。

## 二、总体架构

```text
┌──────────────────────────────────────────────────────────┐
│                        前端 Vue 3                        │
│  Element Plus + Pinia + Axios + ECharts                  │
└──────────────────────────┬───────────────────────────────┘
                           │ HTTP/JSON
┌──────────────────────────▼───────────────────────────────┐
│                    FastAPI 后端服务                      │
│  鉴权、数据源管理、元数据管理、NL解析、SQL构建、任务调度     │
└──────┬───────────────┬──────────────────┬────────────────┘
       │               │                  │
       ▼               ▼                  ▼
┌──────────────┐ ┌──────────────┐ ┌───────────────────┐
│ 业务数据库    │ │  元数据库     │ │ Ollama 本地模型    │
│ SQL Server/  │ │ PostgreSQL/  │ │ Qwen2.5/DeepSeek  │
│ MySQL/PG     │ │ MySQL        │ │ 等本地模型         │
└──────────────┘ └──────────────┘ └───────────────────┘
       │               │
       ▼               ▼
┌──────────────────────────────────────────────┐
│       分析执行层：DuckDB / 结果库 / 文件存储    │
│  上传 Excel 导入 DuckDB，结果表保存或导出 Excel │
└──────────────────────────────────────────────┘
```

**架构说明**：

| 组件 | 职责 |
| --- | --- |
| 业务数据库 | 公司现有 SQL 数据库，**只读连接**，不直接修改原始表 |
| 元数据库 | 保存数据字典、字段别名、业务术语、查询历史、结果表信息 |
| DuckDB | 处理上传的 Excel，将 Excel 临时转成 SQL 表，统一用 SQL 处理 |
| 结果库 | 生成的统计表和明细结果表放在独立结果库/结果 schema，避免污染原始数据 |
| Ollama | 本地模型只做**意图解析**，不直接生成 SQL |

## 三、技术选型

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | FastAPI + Celery + Redis | 异步任务执行长耗时查询 |
| 前端 | Vue 3 + Element Plus + Pinia + Axios + ECharts | 组件化，适合内网管理后台 |
| LLM | Ollama 本地模型（Qwen2.5 / DeepSeek 等） | 只解析意图，输出结构化 JSON，不直接生成 SQL |
| Excel 处理 | pandas 解析 + DuckDB 统一 SQL 查询 | 多 sheet、类型推断 |
| 安全 | 只读账号、RBAC、审计、审批 | 数据不出内网 |

**核心设计原则——混合方案**：采用 **“大模型解析意图 + 确定性代码生成 SQL/表达式”**，而不是让大模型直接生成 SQL。原因：
1. 大模型直接生成 SQL 容易出错，且可能产生危险语句。
2. LLM 只负责识别意图、表、字段、条件、聚合方式，输出结构化 JSON。
3. 后端代码根据 JSON 构建 SQL，安全性更高、可测试、可回归。

## 四、核心业务设计

### 4.1 核心流程

```text
1. 用户选择数据源，输入自然语言
2. 系统读取数据源元数据，构建 Prompt
3. 调用 Ollama 本地模型，输出结构化 JSON
4. 系统校验 JSON：表名、字段名、聚合、条件是否合法
5. 后端代码生成 SQL 或新增字段表达式
6. 前端展示解析结果和 SQL 预览
7. 用户确认
8. 提交异步任务执行
9. 生成结果表/结果文件
10. 前端预览数据并支持下载
```

### 4.2 Prompt 设计示例

```text
你是企业报表助手。根据用户需求，从给定表结构中提取信息，输出 JSON。

【表结构】
表名：sales_order
业务名称：销售订单表
字段：
- region 区域 维度
- order_date 下单日期 维度
- amount 销售金额 度量，默认聚合 SUM
- quantity 数量 度量，默认聚合 SUM

【用户需求】
按区域统计销售额，只看2024年

【输出格式】
{
  "intent": "aggregate",
  "source_table": "sales_order",
  "dimensions": ["region"],
  "measures": [{"field":"amount","agg":"SUM"}],
  "filters": [{"field":"order_date","op":">=","value":"2024-01-01"},{"field":"order_date","op":"<","value":"2025-01-01"}],
  "new_columns": []
}
```

### 4.3 解析结果与 SQL 生成示例

**统计需求**：

```text
输入：按区域和月份统计销售额合计，只看2024年，生成统计表
```

解析 JSON：

```json
{
  "intent": "aggregate",
  "source_table": "sales_order",
  "dimensions": ["region", "month"],
  "measures": [{"field": "amount", "agg": "SUM"}],
  "filters": [{"field": "order_date", "op": "year", "value": "2024"}],
  "new_columns": []
}
```

生成 SQL：

```sql
CREATE TABLE result.rpt_sales_region_month AS
SELECT
    region,
    DATE_FORMAT(order_date, '%Y-%m') AS month,
    SUM(amount) AS total_amount
FROM sales_order
WHERE YEAR(order_date) = 2024
GROUP BY region, DATE_FORMAT(order_date, '%Y-%m');
```

**明细需求**：

```text
输入：给订单明细表增加一列：是否紧急，如果交货天数小于3且金额大于5000就标记为紧急，否则标记为普通
```

解析 JSON：

```json
{
  "intent": "add_column",
  "source_table": "order_detail",
  "new_columns": [
    {
      "name": "is_urgent",
      "type": "string",
      "expression": "CASE WHEN delivery_days < 3 AND amount > 5000 THEN '紧急' ELSE '普通' END"
    }
  ]
}
```

生成 SQL：

```sql
CREATE TABLE result.detail_order_urgent AS
SELECT
    *,
    CASE
        WHEN delivery_days < 3 AND amount > 5000 THEN '紧急'
        ELSE '普通'
    END AS is_urgent
FROM order_detail;
```

### 4.4 两类结果生成

#### 统计表

- 根据解析结果生成聚合 SQL。
- 在结果库中创建新表，命名规范：

```text
rpt_{业务含义}_{时间戳}
例如：rpt_sales_region_month_20250101120001
```

- 支持导出 Excel / CSV。
- 前端展示数据预览（前 100 行）。

#### 明细表

- 默认生成 **“原字段 + 新字段”** 的新结果表，不直接修改原表。
- 写回原表属于高危操作，需要走**审批流程**。
- 原表保护：系统禁止对原始表执行任何写操作。

| 表名 | 说明 | 关键字段 |
| --- | --- | --- |
| `user` | 用户与角色（RBAC） | id, username, password_hash, role, dept |

### 6.2 核心 API 一览

| 模块 | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |
| 认证 | POST | `/api/auth/login` | 登录，返回 JWT |
| 数据源 | GET/POST | `/api/datasources` | 数据源列表/登记 |
| 上传 | POST | `/api/upload` | Excel 上传 → 解析 → 导入 DuckDB |
| 元数据 | GET | `/api/metadata/tables` | 表与字段（展示业务名称） |
| 解析 | POST | `/api/nl/parse` | 自然语言 → 结构化 JSON |
| 任务 | POST | `/api/jobs` | 用户确认后提交异步执行 |
| 任务 | GET | `/api/jobs/{id}` | 任务状态查询 |
| 结果 | GET | `/api/results/{id}/preview` | 结果预览（前 100 行） |
| 结果 | GET | `/api/results/{id}/export` | 导出 Excel/CSV |
| 审批 | POST | `/api/approvals` | 写回原表审批提交/审批 |

### 6.3 关键服务逻辑

- **ollama_service**：封装 HTTP 调用 Ollama `/api/generate`，带超时与重试；Prompt 由元数据动态构建。
- **nl_parser**：对 LLM 输出做 JSON 校验（jsonschema）——表名、字段名必须存在于元数据；聚合函数白名单（SUM/COUNT/AVG/MAX/MIN）；操作符白名单（=, !=, >, <, >=, <=, in, like, year…）。校验失败则提示用户修正。
- **sql_builder**：只依据校验后的 JSON 拼装参数化 SQL；标识符用白名单校验 + 引号包裹，杜绝注入。
- **result_service**：在结果库执行 `CREATE TABLE ... AS SELECT`，登记 `result_table`，计算行数。
- **audit_service**：记录登录、解析、执行、导出、审批等所有关键动作。

### 7.2 交互设计

- 工作台采用 **“对话式输入 + 可选数据源下拉”**。
- 用户不需要知道字段的真实英文名，系统展示**字段的业务名称**。
- 提供示例语句：
  - “按区域统计销售额”
  - “给明细表增加一列：销售金额=单价*数量”
  - “只看2024年的数据”
- **解析结果必须经过用户确认后才执行**，避免误操作。
- 结果默认导出为 Excel，员工可直接打开。

## 八、安全设计

1. **只读账号**：业务数据库使用只读账号连接，物理上禁止修改原始数据。
2. **RBAC**：普通员工 / 部门管理员 / 系统管理员分级授权。
3. **审计**：所有查询、执行、导出行为落审计日志。
4. **审批**：写回原表等高危操作需二级审批。
5. **SQL 安全**：LLM 不直接产出 SQL；SQL 由后端白名单校验后构建。
6. **数据不出内网**：全部组件（含 LLM）部署于内网。

## 九、分阶段实施计划

> 遵循软件工程规范：需求分析 → 概要设计 → 详细设计 → 编码 → 测试 → 部署 → 运维。
> 每个阶段完成后立即测试，**测试通过才进入下一阶段**。

### 阶段 0：需求调研与数据资产盘点
- **任务**：调研各部门常用报表类型；收集 Excel 模板、数据库表结构；梳理字段含义、统计口径、常见明细新增字段场景；编写需求规格说明书和元数据字典初稿。
- **测试**：组织业务人员评审需求文档；确认数据字典字段业务名称准确。
- **交付物**：需求规格说明书、数据字典初稿、数据源清单。

### 阶段 1：基础平台搭建
- **任务**：初始化 Git 仓库与分支规范；搭建 FastAPI 项目骨架；配置日志、配置中心、数据库连接；实现用户登录鉴权；搭建 Docker Compose 开发环境；接入 CI/CD。
- **测试**：配置/日志/鉴权单元测试；登录与健康检查接口测试；CI 流水线正常运行。
- **交付物**：可运行的后端服务、基础前端登录页。

### 阶段 2：Excel 上传与数据预览
- **任务**：文件上传接口；Excel 解析（多 sheet、表头识别、类型推断）；导入 DuckDB 临时表；字段预览接口；前端上传组件和预览表格。
- **测试**：不同类型 Excel 解析单元测试；上传→解析→预览集成测试；边界测试（空文件、大文件、合并单元格、多 sheet）。
- **交付物**：员工可上传 Excel 并在线预览数据。

### 阶段 3：元数据管理与数据源接入
- **任务**：元数据模型与管理接口；数据库数据源只读接入；数据字典（业务名称、维度/度量、默认聚合）维护。
- **测试**：元数据 CRUD 测试；只读连接权限验证测试。
- **交付物**：数据字典可维护，数据库表可被检索。

### 阶段 4：自然语言解析引擎
- **任务**：集成 Ollama 本地模型；Prompt 设计和 schema linking；解析结果结构化输出与校验；前后端解析确认流程。
- **测试**：准备 100～200 条典型业务语句测试集；评估意图识别准确率、字段识别准确率；回归测试（新增样例不破坏已有能力）。
- **交付物**：用户输入自然语言后，系统可识别出表、字段、聚合和条件。

### 阶段 5：统计结果生成
- **任务**：SQL 构建器实现聚合查询；结果表创建；结果预览和导出 Excel；异步任务执行（Celery + Redis）。
- **测试**：统计场景端到端测试；SQL 生成准确性测试；大数据量查询测试；结果导出完整性测试。
- **交付物**：员工可生成统计表并下载 Excel。

### 阶段 6：明细结果生成
- **任务**：解析新增字段需求；生成字段表达式；默认创建“原字段+新字段”新结果表；写回原表功能及审批流程。
- **测试**：新增计算列测试；条件标签列测试；**原表保护测试（不允许直接修改）**；审批流程测试。
- **交付物**：员工可生成带新字段的明细结果表。

### 阶段 7：安全加固与审计
- **任务**：RBAC 权限细化；审计日志完善；敏感操作二次确认；连接信息加密存储。
- **测试**：越权访问测试；审计完整性测试。
- **交付物**：安全加固后的系统。

### 阶段 8：UAT、部署与培训
- **任务**：内网环境部署；业务人员用户验收测试；编写操作手册并培训；试运行和问题修复。
- **测试**：用户验收测试用例；性能测试；安全测试；回归测试。
- **交付物**：系统正式上线、操作手册和培训材料。

## 十、风险与对策

| 风险 | 对策 |
| --- | --- |
| LLM 解析准确率不足 | 限定输出 schema + 白名单校验 + 用户确认环节兜底；持续扩充测试集回归 |
| 员工 Excel 格式千奇百怪 | 阶段 0 盘点模板，解析器支持表头识别/多 sheet/类型推断，解析失败给出明确提示 |
| 误写原始数据 | 只读账号 + 结果库隔离 + 写回审批 + 原表保护测试 |
| 大数据量查询慢 | 异步任务队列 + DuckDB 列式查询 + 结果表行数上限与超时控制 |
| 模型选型效果不佳 | Ollama 可切换模型（Qwen2.5 / DeepSeek 等），Prompt 与解析逻辑解耦 |
